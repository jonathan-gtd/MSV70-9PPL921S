Could be. It might also be handled by the DME. INPA just requests X variable, the DME retrieves and responds. I don't really know, though.
Don't know about the MSV70 for sure, but I'd guess that is the case. On the older DMEs, you send a diagnostic command, and the DME replies with a stream of data. The IPOs have definitions for which bytes in the reply correspond to the data. Probably done that way precisely because BMW wouldn't have to worry about the RAM addresses changing with updates.

If you can identify the section of code where the diagnostic requests are handled (whether BMW format or OBDII), that can be a great way to label some RAM addresses and figure out what the DME does with those.

Search routine is working pretty well now. I've increased the speed quite a bit (and learned a lot). MSV70 searches are matching at about 75% on the binaries I have - that's without anything more advanced than a 1:1 search (no partial matches etc).

Searching my first MSV80 file now. constants/single bytes will be hardest to find - on MSV70, empty space is filled by 'FF'. On MSV80, empty space is filled by '00'. When searching for single bytes, you have to include some bytes around it to get a match, but now I have to determine what is empty space on MSV80, and what is really supposed to be "FF". Plus the order of everything is way different - the maps are the same, but they are not in the same binary order at all.

I'm expecting low match rates on single bytes, but curves and maps should still be pretty good. Also, anything on MSV70 that is all "00 00" etc. will give a false positive as about 75% of the MSV80 binary is empty space. One saving grace is MSD80 is based on MSV70, so potentially a lot of these parameters exist in MSD80 so I can use that as a cross reference as well.

At least the byte flip from big endian to little endian is easy..
