DataLogs
I finally managed to get back to work with the Testo Data logging but I have not bee able to achieve the data rates I want. It's a complicated discussion but we are forced to choose between fast message rates or more complete data per message.

As a sample, I have attached a log with a lot of data but a low message count. The way Testo works, I could pull 70% of the data from this custom job but the speed would only improve by 20%. Standard jobs are faster but don't have much data, running multiple standard jobs is really slow.

I can add custom calculated fields to the Testo jobs such as HP or VE providing the required data is already being collected in the job. In other words to calculate HP you must already be polling the torque and RPMs.

I've been taking my data runs from the side of the freeway, Starting slowly and going to full load near the middle of first gear and holding all the way into the middle of third. This give me good data through a full gear (2nd) and through the two shifts. I'm not interested in tearing up tires to get inconstant data on the launches. A good pull through 3rd or 4th would be nice but I don't have an open run way for that.

Magalog seems to be the best program to read the output files.


Edit: Notice the Intake Air temperatures! If Florida in August. The Temp starts out very high and drop through the pull.

Does anyone have any suggestions to improve the process?

OK, here's what I've been working on all this time... a 100% complete MSV70 XDF (all 8917 parameters!). You have to use it with the included binary (or at least one with the same program version, 730).

This is really only useful for research purposes, since the 730 software version isn't up to date and nobody likely has it left on their car. Updated XDFs for newer versions (including MSV80) are next on the list.

A translation mechanism is built in, I just need to build the database of translations. There are too many to do by hand, so I'll probably use Google for it and just fix the ones that are obviously mistranslated. For now, you must read auf Deutch!

BTW, there is a bug in TunerPro that doesn't allow it to use more than 255 categories. MSS70 has almost 900 categories, which breaks TunerPro. Just sort it by "Parameter Type" or "Ordered List". I have something in mind to deal with this but I need to finish building my tools first.

Just starting on my search tool. curves and maps will be easiest, single bytes the most difficult. Anyway, with some rough hacking I successfully got it to find maps in the latest software version (921).

I'm not really a search engine expert, but I have a few ideas for strategies:
1st attempt: search for the map at the default address(730 software). If it matches, great!
2nd attempt: search for an exact match of the map. Most of them will be unchanged, but not all.
3rd attempt: search for partial matches of each map. I figure I can use some statistics to calculate a confidence ratio, selecting the match that seems the most likely to be the correct one. This will also work for single byte values (where by hand, I'd search for strings of nearby bytes until I find the one that looks correct).

Anyway, just thinking out loud - nothing you guys will care about, at least until I have XDFs for versions other than the original MSV70 release.

this will make searches in MSV80 much easier as well. They are all basically the same, except MSV80 uses a different byte order. That makes it a pain in the ass to search by hand, but no real difference using an algorithm..
